# workmate_chat_send

Send one message into a stateful 1C:Workmate conversation started with workmate_chat_create, as a background job returning its jobId. The first send starts the cloud conversation; later sends land in the SAME one, so Workmate keeps the full context. By default (shareMcpTools) Workmate may call EDT-MCP's own tools through this plugin, so it can READ the project and CHANGE code and metadata. Poll the job with get_job_status; read the finished exchange with workmate_chat_history. Parameters and examples: get_tool_guide('workmate_chat_send').

## Parameters
| Parameter | Required | Type | Description |
| --- | --- | --- | --- |
| chatId | yes | string | Chat id returned by workmate_chat_create. |
| message | yes | string | Non-empty message or instruction to send into this chat. |
| timeoutSeconds | — | integer | Total wall-clock budget for this send across all get_job_status polls, in seconds; defaults to 600 and accepts 1 to 3600. After this budget the job is failed - unless the request had already reached Workmate, which cannot be taken back: the job then reports Workmate's own outcome rather than a retryable timeout, because a retry would run the same work twice. |
| waitSeconds | — | integer | Maximum time this call may wait for completion before returning its job snapshot, in seconds; defaults to 5, accepts 0 to 45. Use 0 to return immediately. This does not extend the job's total timeoutSeconds budget. |
| shareMcpTools | — | boolean | When true (default), the message is prefixed with instructions that let Workmate call EDT-MCP's own tools through this plugin's in-process bridge, so it can inspect the real project instead of answering from general 1C knowledge. |
| maxToolRounds | — | integer | Optional positive limit for Workmate's internal tool-call rounds for THIS send; overrides the chat's maxToolRounds (default 80) when provided. |

## Guide
Sends one message into a stateful 1C:Workmate conversation created with
`workmate_chat_create`, as a background job. The call returns a job snapshot; poll the jobId
with `get_job_status` until it reaches a terminal state, then read the finished exchange with
`workmate_chat_history`.

The first send of a chat starts the cloud conversation; every later send re-enters the SAME
one through the stored conversation cursor, so Workmate sees the whole history.

## Examples

Send and return immediately:

```json
{
  "chatId": "2d3f...",
  "message": "List the catalogs of this configuration and their purpose",
  "waitSeconds": 0
}
```

Poll, then read the answer:

```json
{"tool": "get_job_status", "arguments": {"jobId": "<id from send>", "waitSeconds": 45}}
```

```json
{"tool": "workmate_chat_history", "arguments": {"chatId": "2d3f...", "limit": 2}}
```

Then continue the SAME conversation with a follow-up — no context needs to be repeated:

```json
{
  "chatId": "2d3f...",
  "message": "Now detail the largest one"
}
```

## Rules

- ONE send per chat at a time: a second send while one is running is refused, because two
  in-flight sends would fork the cloud conversation. Poll the running job instead.
- The conversation cursor advances only after a send that COMPLETED. A failed send never
  moves it; the journal records the error.
- Workmate's tool loop can READ and CHANGE the project (metadata, BSL) when shareMcpTools is
  on. A timeout does not undo changes already made — inspect the project before retrying.
