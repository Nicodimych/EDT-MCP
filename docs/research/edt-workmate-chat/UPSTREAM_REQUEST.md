# Feature request: полноценная управляемая MCP-беседа с 1С:Напарником

Нужен внешний API, позволяющий вести полноценную беседу с 1С:Напарником в уже запущенном EDT: отправлять сообщения в одну беседу, получать ответы и события инструментов, отвечать на уточнения и подтверждения, продолжать после переподключения.

Сейчас ask_workmate полезен для разового запроса и выполнения родных инструментов, но внешний клиент не получает полноценной модели диалога. `mode="chat"` передаёт работу панели; это не заменяет получение результата и последующее управление беседой по MCP.

## Проверенный технический фундамент

На EDT 2026.2.1.3, Напарнике 1.0.8.v202609241142 и EDT-MCP 2.20.1 проведён эксперимент без изменения установленных плагинов:

1. Через `ask_workmate(workmateTool="JShell", ...)` выполнен Java-код в постоянной JShell-сессии `edt-mcp`.
2. Получен `ConversationFacade` через `BaseActivator.getInstance(ConversationFacade.class)`.
3. Выполнен `sendAsync(SendUserMessageRequest, ICancellationToken, IConversationProgressListener)` с `skillName="custom"`, внутренним `chat=true`.
4. После ответа сохранена `SendMessageResult.getSession()`.
5. Следующее сообщение отправлено с этой сессией и `forceNewConversation=false`.
6. Получен ответ с данными предыдущего хода; идентификатор беседы остался прежним. Отдельный контрольный маркер также сохранился.

В инструментальном тесте Напарник самостоятельно прочитал свойства открытой конфигурации через JShell → in-process EDT-MCP bridge, ответил и обработал уточнение по уже полученным данным.

Подтверждены серверные вызовы `TodoWrite`, `Task`, `TaskResult`, `mcp__knowledge-hub__Search_ITS`, `mcp__knowledge-hub__Fetch_ITS`. Получено содержимое конкретной статьи ИТС по переданной ссылке.

В отдельном экземпляре исполнителя к родным инструментам добавлен собственный `IMcpTool`. Сервер вызвал его по имени; локальный обработчик выполнился один раз, вернул уникальную метку и версию установленного стороннего плагина, а модель использовала результат. Глобальный реестр штатной панели при этом не изменялся.

Дополнительно проверен штатный `1cedtcli ask` версии Напарника 1.0.8: его JSON имеет conversationId, но команда не принимает сессию для следующего запуска, каждый runTurns начинает с session=null/forceNew=true. Внутренний autoContinue относится к одному заданию. Кроме того, в нашей установке factory возвращает DisabledAskCommand при experimental=false. Поэтому CLI в текущем виде не заменяет запрашиваемый stateful MCP API.

## Желаемый интерфейс

Имена ниже — предложение, а не существующие инструменты:

- `workmate_chat_create`: проект, профиль/skill, политика инструментов; возвращает chatId и возможности текущей версии.
- `workmate_chat_send`: chatId, message, clientRequestId, expectedRevision; возвращает turnId сразу.
- `workmate_chat_events` / `workmate_chat_status`: cursor, ограниченное ожидание; текст, tool calls/results, вопросы, подтверждения, терминальный результат.
- `workmate_chat_reply`: interactionId и типизированный ответ на вопрос или запрос подтверждения.
- `workmate_chat_cancel`: отмена конкретного хода с подтверждаемым состоянием.
- `workmate_chat_list` / `workmate_chat_resume`: обнаружение доступных бесед, подключение/восстановление; явно различать локальную запись и облачную историю.
- Управляемое расширение каталога инструментов: описание + исполнитель либо явный внешний callback с correlation ID.

Критично не ограничиться ещё одним вариантом однократного ask_workmate. Главный сценарий: модель задаёт уточняющий вопрос, внешний клиент видит его структуру, отвечает, и тот же ход/диалог корректно продолжается.

## Особенности, которые нужно учесть

- Есть три разных уровня сессий: HTTP MCP transport, JShell REPL и ConversationSession (`conversationId` + `replyToMessageUuid`). Их жизненные циклы различаются.
- Встроенный `allowedTools` фильтрует передаваемые описания. Сам по себе это не доказанная граница запрета исполнения: локальный dispatch использует полный реестр.
- Родной каталог Напарника и каталог EDT-MCP независимы. Нативный JShell может обращаться к мосту, но Read/GetProjects и другие родные инструменты не требуют этого моста.
- Неизвестные локальному исполнителю вызовы могут быть серверными. В исследованной версии они попадают в `unknownCalls` и продолжаются с `status="accepted"`; нельзя автоматически превращать их в `Tool not found`.
- Перечень SERVER_TOOLS в Java не исчерпывает фактические имена: встречаются `mcp__knowledge-hub__...`; пользователь подтвердил `mcp__web__fetch` в панели.
- Имя инструмента и его описание не создают исполнитель автоматически.
- У панели и native API могут различаться разрешения, инструкции, загрузка project rules и обработка интерактивных карточек. Требуется проверка паритета.
- Одновременная работа пользователя в панели и внешнего клиента требует защиты от продолжения по устаревшему parent UUID и неявного создания ветки.

## Обнаруженные сбои

- Пустые ответы, таймауты и единичный `Failed to create conversation`.
- `IndexOutOfBoundsException: Index -1 out of bounds for length 0` в `Conversations.applyDelta`, строка 742: обработчик обращается к `toolCalls.get(delta.index)` без проверки отрицательного индекса. Это код установленного Напарника; происхождение отрицательного индекса отдельно не установлено.
- Исследование с планом и подзадачей превысило лимит 10 инструментальных раундов. Продолжение с последнего неподтверждённого серверного tool call позволило получить итоговый ответ. Такой recovery нельзя обобщать на повторное выполнение локальных операций.
- После перезапуска EDT теряются объекты JShell. Старый MCP session ID получает 404, требуется новый initialize. Автозапуск MCP после перезапуска в нашем окружении не произошёл.
- Пользователь сообщил о необходимости перезапуска EDT после серии экспериментов; причинная связь с конкретным вызовом не установлена. Нужны отдельные проверки отмены, освобождения подписок и потоков.

## Критерии приёмки

1. Внешний клиент проходит три хода в одной беседе, включая уточняющий вопрос модели.
2. Чтение открытого проекта выполняется родным инструментом и через EDT-MCP bridge; результаты различимы в событиях.
3. Серверный поиск/чтение ИТС и подзадача завершаются без потери tool results.
4. Карточки одиночного/множественного выбора и подтверждение изменения работают по MCP без DOM-автоматизации; отказ также тестируется.
5. Свой безвредный инструмент объявляется, вызывается по имени и возвращает коррелированный результат.
6. Переподключение клиента не дублирует сообщение/операцию. Перезапуск EDT даёт понятное восстановление или явное состояние interrupted.
7. UI-ход, выполненный между двумя внешними запросами, обнаруживается; устаревший parent не используется молча.
8. Пустой ответ, отрицательный индекс, исчерпание бюджета и отмена имеют явные диагностируемые состояния.

Готовы предоставить техническое досье, воспроизводимые JShell-примеры, минимальный MCP-клиент, карту исходников и обезличенные результаты экспериментов. Необходимость конкретных внутренних API и их совместимость желательно согласовать с разработчиками 1С:Напарника.
