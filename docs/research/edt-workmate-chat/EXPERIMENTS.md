## E02–E03: непрерывный диалог

Raw контроль: conversationId `a0d51a1e-4f78-47e9-8652-b20debab42f7`. Информация о конфигурации в этом raw опыте задавалась в вопросе, поэтому это доказательство контекста, а не чтения проекта.

Рабочая native беседа: `973b5cd6-b191-4209-98f4-61e08d27ba59`. Проект `АвтодействияТест`. Первый ход получил фактические свойства через get_configuration_properties: имя `КомплекснаяАвтоматизация`, синоним `1С:Комплексная автоматизация 2`, версия `2.5.26.118`, совместимость `8.3.27`. Напарник спросил, какую характеристику исследовать дальше. Уточнение про режим запуска и язык вернуло `ManagedApplication` и `Russian`.

Зафиксированный после этого replyToMessageUuid: `17d88eaa-16ef-487b-a492-8b8353647831`. Это **исторический** курсор: позднее в той же беседе были другие ходы. Нельзя использовать его как актуальный последний reply при восстановлении.

Первый ход использовал отдельный facade с диагностическим сериализатором; продолжение прошло через штатный singleton. Это подтверждает значение ConversationSession, а не обязательность конкретного объекта facade в памяти.

Обычный текстовый уточняющий вопрос подтверждён. Структурированные карточки выбора, отказ/подтверждение изменения и пауза waiting_for_user через native API ещё не проверены.

## E05–E06: серверные инструменты и ИТС

В потоке наблюдались три Search_ITS, два Fetch_ITS, TodoWrite и Task/TaskResult. Имена ИТС: `mcp__knowledge-hub__Search_ITS`, `mcp__knowledge-hub__Fetch_ITS`; это не инструменты из локального реестра 26 и не инструменты EDT-MCP.

Примеры документов:

- `https://its.1c.ru/db/pub1cerpmto/content/31/hdoc` → «Номенклатура и сопутствующие ей справочники», внутренний ID `its-pub1cerpmto-31-hdoc`, примерно 10 152 символа результата с оболочкой.
- Документ ERP 2.5 LTS, ID `its-erp25ltsdoc-5-hdoc`, примерно 10 296 символов результата.
- Отдельный запрос `https://its.1c.ru/db/utovio/content/97/hdoc` → ID `its-utovio-97-hdoc`, «Для каких целей используются характеристики товаров? Чем они отличаются от свойств товаров?», примерно 3 011 символов результата.

Сами статьи в пакет не включены. При сравнении с анонимным web-просмотром тело статьи не получено, но HTTP был 200, и строгий контроль платного доступа не проводился. Вывод ограничен следующим: **Напарник смог получить эти документы своим серверным инструментом. Возможность читать любую закрытую ссылку или обходить авторизацию не доказана.**

Исследование остановилось на `Too many tool rounds` при maxToolRounds=10. Последний запрос был TodoWrite. Для этого конкретного серверного шага сформирован штатный accepted и продолжен collectAssistantResult с повышенным лимитом. После этого получен окончательный ответ.

Этот способ — диагностическое подтверждение возможности продолжения. Он не годится как универсальное повторение сбойного шага: локальный инструмент мог уже выполнить изменение, а повтор приведёт к дублированию. В продукте нужен сохранённый журнал tool_call_id, результата и подтверждения.

## E07: собственный инструмент

Добавлен только в отдельный executor/facade, исходный реестр остался 26, тестовый стал 27. Локальный инструмент читал версию Xelgo bundle и возвращал JSON:

```json
{
  "label": "ГВОЗДЬ-8042",
  "proof": "LOCAL-26f7b7e2-a608-49bc-8792-698c06ec2670",
  "call_number": 1,
  "xelgo_version": "1.1.22.v202608042058"
}
```

Уникальная proof создана обработчиком до вызова и не дана модели в prompt. Наблюдались callbacks start/end, calls=1 и совпадение proof в окончательном ответе. Это сильнее, чем согласие модели «инструмент доступен».

Экспериментальные Java-объекты исчезли после перезапуска EDT. Обычная панель автоматически этот инструмент не получила. Нужна поддерживаемая точка регистрации или собственный adapter.

## E09–E10: поправка по общему интернету

Первый внешний запрос на WebSearch/WebFetch дал отрицательный ответ модели без tool events. Другой запрос с native skill edt завершился пустым текстом. По этим двум наблюдениям нельзя было заключать, что web fetch вообще отсутствует.

Пользователь затем открыл последний чат в панели, повторил запрос и сообщил фактический вызов `mcp__web__fetch` для example.com. Напарник при этом указал, что `mcp__web__search` отсутствует. На следующую просьбу «погугли» он обращался к обычным страницам, включая поисковики; Google не дал удобного текста, Яндекс потребовал SmartCaptcha, затем использовались другие сайты.

Это подтверждает web-чтение в панели и поиск посредством посещения URL. Отдельный WebSearch не подтверждён. Новостные выводы модели о сбоях сервисов 1С не проверялись и здесь не используются как факты.

Следующая необходимая проверка — повторить именно `mcp__web__fetch` через native внешний цикл с фиксацией tool_call_id и результата, а затем синхронизировать API после хода из панели.

## Сбои, которые стоит передать разработчикам

| Симптом | Что известно | Чего не знаем / нужная диагностика |
|---|---|---|
| `IndexOutOfBoundsException: Index -1 out of bounds for length 0` | Стек Conversations.applyDelta:742 → processStream:664 → lambda$10:549; bytecode не защищает отрицательный index | Не сохранён полный исходный SSE, источник -1 не установлен; нужен обезличенный fixture |
| Пустой ответ / timeout 30–120 с | Были и в ask_workmate, и в отдельных native пробах | Не считать автоматически ошибкой session или отсутствием tools; разделить transport, cloud, parser и конечный результат |
| `Failed to create conversation` | Первая исследовательская беседа не создалась; продолжение известной сессии сработало | Повторяемость и ответ backend не исследованы |
| `Too many tool rounds` | Реальные серверные инструменты работали, но ответ не завершился в 10 раундов | Нужен resumable checkpoint, отдельный счётчик ходов и видимый partial result |
| Cooperative cancel | Флаг отмены передавался через token | Прекращение всех сетевых запросов и фоновых работ не доказано |
| EDT пришлось перезапустить | Сообщение пользователя после опытов | Причина не установлена; не приписывать конкретному плагину без thread dump/log |
| MCP не поднялся автоматически | Пользователь запустил вручную | Настройки автозапуска и причинность не проверены |
| Старый MCP session после restart даёт 404 | Новый initialize с protocol header исправил соединение | Это транспортная сессия, а не ConversationSession |

Нельзя исправлять index=-1 механической подстановкой 0: при нескольких tool calls можно склеить чужие аргументы. Нужна проверка протокола, tool ID, порядка delta и финального content.

## Что ещё не доказано

Ответ на карточку/подтверждение; durable resume после restart; свежесть API курсора после UI; гарантированная отмена; одновременные независимые чаты; долговременная регистрация custom tool; перечень реально доступных серверных инструментов; соответствие permissions и skill rules штатной панели при прямом API.
